# Interlock Data Model

Status: normative design contract, 2026-07-19.

## Design rules

- PostgreSQL is the only durable authority. In-memory structures are disposable.
- Facts are propositions, not prose blobs. Documents and observations preserve
  source wording but never masquerade as current canonical truth.
- Corrections are structural state transitions. A correction cannot coexist as
  an ordinary competing search result with the value it replaced.
- Scope, provenance, time, authority, and epistemic status are mandatory data,
  not metadata added after retrieval.
- Rows are append-oriented. Canonical changes close validity intervals and add
  audit events; destructive deletion is reserved for retention and privacy law.

## Identity

UUID primary keys are generated by the service. Human-readable external IDs are
separate, unique, and stable across export/import. All timestamps are UTC
`timestamptz`.

`scopes` stores a normalized identity tuple:

| Field | Meaning |
| --- | --- |
| `tenant_id` | Administrative isolation boundary |
| `user_id` | Owner identity |
| `consumer_id` | Codex, Claude, or another authorized client |
| `project_key` | Durable project identity |
| `repository_key` | Normalized repository remote identity |
| `thread_id` | Conversation/task identity |
| `session_id` | One execution session |

Nullable dimensions mean broader applicability, never unknown identity. An
unknown dimension is represented explicitly on the source event and cannot be
promoted to a broad scope by omission.

## Core relations

### `observations`

Immutable, idempotently ingested events. Required fields include source event
ID, scope, actor, event kind, observed time, redacted searchable content,
encrypted raw-content reference when retained, content hash, schema version,
and ingestion time. `(tenant_id, consumer_id, source_event_id)` is unique.

Observations can be searched as history but are never canonical recall rows.

### `candidates`

Extractor proposals derived from one or more observations or documents. Each
stores normalized subject, predicate, object, proposed scope, authority claim,
epistemic status, confidence, extraction model and prompt versions, evidence
links, and workflow state.

Workflow states are `pending`, `accepted`, `rejected`, `quarantined`, and
`needs_review`. Retrying an extractor uses a derivation key and cannot create a
second logically identical candidate.

### `predicates`

A registry defining memory semantics. Each predicate declares:

- value type and validation schema;
- cardinality: `single` or `set`;
- temporal behavior: durable, expiring, or observed-state;
- allowed scope levels;
- conflict and merge policy;
- minimum authority for automatic canonicalization;
- whether owner confirmation is required.

Unknown predicates may enter the candidate lane but cannot become canonical
until registered.

### `propositions`

Versioned canonical memory. Principal fields are scope, subject, predicate,
typed object, normalized object hash, authority tier, epistemic status,
`valid_from`, `valid_to`, `recorded_at`, source provenance, and status.

Statuses are `current`, `superseded`, `invalid`, `disputed`, and `quarantined`.
Ordinary recall reads only `current` rows whose validity includes the query's
effective time.

For single-cardinality predicates, a partial unique constraint ensures at most
one current proposition per `(scope_id, subject_key, predicate_id)`. Acceptance
of a replacement closes the old row and inserts the new row in one serializable
transaction.

Set predicates use uniqueness over `(scope_id, subject_key, predicate_id,
object_hash)` and track membership independently.

### `proposition_edges`

Typed links between propositions: `supersedes`, `corrects`, `supports`,
`contradicts`, `narrows`, and `derived_from`. Edges have provenance and are
audited. `supersedes` and `corrects` must agree with validity/status changes;
deferred constraints verify this at commit.

### `documents`

Versioned references to canonical external material such as documentation
pages, repository files, and runbooks. The table stores identity, revision, checksum,
authority domain, scope, fetched time, and content chunks. A document supports
propositions; it is not itself a proposition unless the retrieval intent is
`procedure` or `why`.

### `handoffs`

Append-only, exact-project continuation state with creation and expiry times.
Handoffs never have embeddings in the canonical index, never become candidates,
and cannot be promoted. Durable truths in a handoff require an independent
explicit memory write.

### `audit_events`

Append-only record of every canonical mutation, verification, promotion,
invalidation, policy change, privileged raw-content access, and export. It
stores actor, authorization context, before/after IDs, reason, request ID, and
timestamp.

### `outbox`

Transactional events for embedding, snapshot refresh, export, and observation
acknowledgement. Workers claim with `FOR UPDATE SKIP LOCKED`; handlers are
idempotent by event ID. An acknowledged write is durable before a client receives
success.

## Authority and epistemic state

Authority is an ordered enum, not a floating score:

1. owner instruction;
2. mechanically verified observation;
3. canonical documentation;
4. repository state;
5. trusted agent report;
6. inference;
7. raw history.

Epistemic status is orthogonal: `verified`, `asserted`, `inferred`, `uncertain`,
or `disputed`. Confidence never overrides authority. Recency only breaks ties
inside the same authority tier and applicable scope.

## Retention and secrets

Redacted content and structured propositions follow their declared retention
class. Raw sensitive payloads live in a separately encrypted store referenced by
opaque ID, never in embeddings or logs. Crypto erasure removes the wrapped data
key; derived searchable material is deleted by provenance traversal and the
operation is recorded in the audit log.

## Required database invariants

The migration suite must prove:

- no two current single-cardinality values exist for the same canonical key;
- no superseded row has an open-ended validity interval;
- every canonical row has at least one provenance record;
- every correction has a matching audit event and structural edge;
- handoffs have no path into candidate or canonical tables;
- tenant and user scope are present on every durable row;
- outbox replay cannot duplicate observations or canonical transitions.
